> 诊断日期：2026-10-18
> 诊断方式：架构师静态代码审查 + QA 运行时实测 + 主理人交叉复核

## 一、总体结论

**这是一个"骨架健康、工程护栏缺失"的项目。**

业务逻辑设计得相当干净——分层清晰、无 god class（最大类 182 行）、核心的积分双轨规则经实测完全成立、无 SQL 注入、无 XSS、无路径穿越。当前运行时状态也健康：13 个页面全部 200、数据三路校验全等、基线 ERROR 为 0。

但项目**缺少三道基础护栏**：没有版本控制、没有自动化测试、没有并发安全设计。这意味着现在的一切"健康"都建立在"单用户、串行操作、没人手抖"的前提上。

> ⚠️ 诊断期间项目正在并发修改（16:34–16:42 新增 LoginController / LoginInterceptor / AuthService 登录鉴权模块）。本报告是基于该时段快照，结论需结合最新代码复查。

## 三、问题清单（合并去重，按优先级）

### 🔴 P0 — 必修（5 项）

| # | 问题 | 证据位置 | 影响 | 修法 | 成本 |
|---|------|---------|------|------|------|
| P0-1 | **积分并发丢失更新** | `PointService.java:74-112` | 两个请求同时读到 balance=100，各加 10 后写回 110，实际只加一次 | 乐观锁 / `SELECT ... FOR UPDATE` / 原子 SQL `SET balance = balance + ?` | 中 |
| P0-2 | **审批与兑换的并发窗口** | `TaskService:114-126`、`RewardService:64-94` | 串行安全（有状态检查），但并发下两个请求同时通过校验会重复加分/扣分 | 同 P0-1，加锁或原子操作；`claim` 补去重查询 | 中 |
| P0-3 | **默认口令 123456** | `data.sql:115-120` | 密码虽用 PBKDF2 哈希（这点做得对），但默认口令未强制修改 | 首次登录强制改密，或种子数据生成随机初始密码 | 低 |
| P0-4 | **构建产物 = 运行时文件** | `run.bat:29` + `mvn package` 输出同路径 | 这就是"打包前必须停 java 进程否则 jar 损坏成 100KB"的**根因** | 打包后拷 `target/*.jar` 到 `dist/` 带时间戳运行 | **极低（0.5 人时）** |
| P0-5 | **负分任务被静默转正** | `PointService.java:44` `Math.abs(points)` | 家长填"拖延 -3"这类惩罚任务，审批后孩子**反而加 3 分**，全程不报错。`addManual` 亦无范围校验，`schema.sql:99` 无 CHECK 约束 | `Math.abs` 改为显式校验 `points > 0`，非法则拒绝并提示 | **极低（一行级）** |

> **关于 P0-1 的措辞修正**：初版报告称"非原子"，经复核不准确。`PointService` 的 42/50/58/66 行**均有 `@Transactional`**，原子性是有保障的。真实风险是"原子但并发不安全"——`@Transactional` 保证要么全成功要么全回滚，但不解决丢失更新（lost update）。修法是加锁或原子 SQL，**不是补事务注解**。

### 🟠 P1 — 本迭代建议修（5 项）

| # | 问题 | 证据位置 | 影响 | 修法 |
|---|------|---------|------|------|
| P1-1 | 不存在孩子 ID → **500** | `PetService.getPetCard:34-36` | `/kid/{id}`、`/pets/{id}` 传错 ID 直接 500 页 | child 判空后抛 `IllegalArgumentException`，复用现有友好提示 |
| P1-2 | 删除不存在任务 → **500** | `TaskController.delete` | 先取值后判空 | 调整判空顺序 |
| P1-3 | 日志不可审计 + DEBUG 全开 | `start-server.bat:13` 用 `>` 导致每次重启截断；诊断期间重启 ≥3 次，16:40–16:46 日志段已全丢；DEBUG 占 2201/2607 行 | 出问题时查不到任何历史，等于没有日志 | `>` 改 `>>` + rolling policy + 常态 INFO |
| P1-4 | `/board` 免鉴权返回全量数据 | `WebConfig.java:37`（注释已注明"如需保护删掉本行"） | 局域网任何人可见孩子姓名、积分、照片 | 家庭内网可接受；若介意请删掉该行 |

### 🟡 P2 — 可选优化（10+ 项，详见两份分报告）

- `/board` 一次请求触发 **17 条 SQL**，其中 8 条是重复查 10 行的 `pet_level` 配置表（占 47%）→ 加缓存

- CSS 版本戳靠手工递增 `?v=N`，易遗漏

## 五、三道基础护栏（根因级建议）

P0/P1 修完仍不够。以下三项是所有风险的**放大器**，建议优先补齐：

1. **接入 Git** —— 60+ 文件、迭代十几轮，当前任何误操作都无法回滚。这是最大的单点风险，成本却只要几分钟。
2. **补核心链路自动化测试** —— `spring-boot-starter-test` 已在 pom 里躺着没用。优先覆盖积分双轨规则、兑换幂等、灵宠升级三个核心场景，这三块一旦回归出错最难发现。
3. **分离构建产物与运行时** —— 即 P0-4，顺手可解。

## 六、修复后的验证方式

项目已有 `scripts/verify.sh` 端到端自检脚本（12 页检查 + 业务规则校验）。建议修复后：

1. 跑 `scripts/verify.sh` 确认页面与业务规则全绿
2. QA 补跑第 2 轮回归（重点：幂等、负分、异常入参）
3. 将 `verify.sh` 接入日常改动流程，替代手工点页面

## 七、一句话总结

> 业务设计的水准高于工程保障的水准。代码写得干净，但**没有版本控制、没有测试网、并发下会算错分**。
> 按第 1 批（产物分离 + 去 Math.abs + 三处判空 + 接 Git）开刀，半天就能拿到绝大部分收益。
